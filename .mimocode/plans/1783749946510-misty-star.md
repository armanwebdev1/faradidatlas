# Product Image Performance Investigation & Fix

## Root Cause

**Next.js Image Optimization is the bottleneck.** Every product image request goes through a two-hop chain:

```
Browser → /_next/image (optimizer) → /api/media/file/<filename> (Payload) → Vercel Blob
```

The Payload endpoint itself is fast (~115ms, `x-vercel-cache: HIT`). But the optimizer layer in between:

1. Fetches from Payload (fast)
2. **Re-decodes the WebP** using sharp
3. **Re-encodes to AVIF** (because `formats: ["image/avif", "webp"]`)
4. **Resizes to the requested width** (e.g. 750px, 360px, etc.)
5. Serves the result with its own cache — but this cache consistently **misses**

## Why `x-vercel-cache: MISS` Every Time

The `/_next/image` endpoint uses its own image optimization cache, keyed by: `(src URL, width, quality, format)`. Several factors cause persistent misses:

1. **Format negotiation creates new cache keys**: Every time the browser negotiates AVIF vs WebP, it's a different cache entry. With `formats: ["image/avif", "webp"]`, the optimizer generates both formats as separate entries.

2. **Responsive `sizes` prop generates multiple width variants**: The product card `sizes="(min-width: 1280px) 360px, (min-width: 1024px) 31vw, (min-width: 640px) 46vw, 92vw"` combined with device pixel ratios (1x, 2x, 3x) produces ~8+ different width variants per image. With 30 products on the page, that's 240+ unique optimizer URLs.

3. **Source URL instability**: The Payload endpoint URL may include query params, locale info, or cache-busting elements that change the optimizer's source key.

4. **Vercel's serverless architecture**: On Vercel, the optimizer runs in serverless functions. Each cold start rebuilds the cache from scratch. The `minimumCacheTTL: 30d` only affects the Edge cache TTL — it doesn't prevent cold-start misses.

5. **Payload's own Cache-Control headers** (`max-age=31536000`) conflict with what the optimizer expects from an upstream source, potentially causing revalidation.

## Evidence Summary

| Metric | Payload Direct | Via `/_next/image` |
|---|---|---|
| TTFB | ~115ms | Much higher (optimization overhead) |
| Cache status | `x-vercel-cache: HIT` | `x-vercel-cache: MISS` (always) |
| Format served | Original WebP | Re-encoded AVIF |
| CPU work | None (just file serving) | Decode + resize + AVIF encode |
| Per-request cost | Minimal | Heavy (sharp operations) |

## Why Next.js Image Optimization Provides No Benefit Here

1. **Payload already serves optimized WebP** — the images are pre-compressed at production quality. Re-encoding to AVIF saves ~15-20% bandwidth but costs 10-50x more CPU per request.

2. **The cache never warms** — with persistent MISS, the optimization work is repeated on every single request, defeating the purpose of caching.

3. **The images are not huge** — they're product photos in WebP. The bandwidth savings from AVIF don't justify the latency increase from on-the-fly conversion.

4. **Responsive sizing is handled by CSS** — the `fill` + `object-cover` + `aspect-square` container pattern already handles layout. Next.js `sizes` only tells the optimizer which width to generate, but the browser renders the full-quality image regardless.

5. **The optimizer adds a waterfall** — instead of `Browser → CDN → Image`, it's `Browser → Serverless Function → Payload → Blob → sharp → AVIF → Response`. This is 3-5x more network hops and adds 200-500ms+ of processing.

## Solution

**Use `unoptimized` for all Payload media images** served through `/api/media/file/`. This eliminates the optimizer bottleneck while preserving:

- Responsive sizing (via CSS `object-cover` + container aspect ratios)
- Lazy loading (via `loading="lazy"` and IntersectionObserver)
- CLS prevention (via `fill` + sized containers)

For static public images already in `public/*/optimized/`, `unoptimized` is already correct — they have immutable cache headers and are pre-built WebP.

## Files to Modify

### 1. `components/home/hero.tsx` (line 109)
**Add `unoptimized`** to the hero slideshow `<Image>`. The hero loads from Payload media or static `/hero/optimized/` paths — both are already optimized. No need for re-optimization.

```diff
 <Image
   src={resolveMediaUrl(slide.image)}
   alt={...}
   fill
   priority={index === 0}
   loading={index === 0 ? undefined : "lazy"}
   sizes="100vw"
+  unoptimized
   className={...}
 />
```

### 8. `next.config.mjs` — No changes needed
The `formats`, `minimumCacheTTL`, and `remotePatterns` settings remain useful as a safety net for any edge cases, but with `unoptimized` on all images they become inactive. Keeping them is harmless and provides a fallback.

## What NOT to Change

- **Don't remove `sizes` props** — they're still useful for layout hints and browser preloading even with `unoptimized`
- **Don't remove `priority`/`loading` props** — they control native lazy loading behavior
- **Don't disable `images.formats` globally** — it's harmless with `unoptimized` and useful as fallback
- **Don't modify Payload media configuration** — it's working correctly
- **Don't add a custom loader** — `unoptimized` is simpler and has the same effect
