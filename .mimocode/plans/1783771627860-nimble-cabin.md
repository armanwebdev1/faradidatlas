# Fix: Vercel Build Failure — PostgreSQL Connection Pool Exhaustion

## Problem

The Vercel build fails with `EMAXCONNSESSION: max clients reached in session mode - max clients are limited to pool_size: 15` during `next build`. The Supabase Postgres server enforces a 15-connection limit, and the build process exceeds it.

## Root Cause

During `next build`, Next.js statically renders **30+ pages** (10 route patterns × 3 languages). Every page embeds `<Header>` and `<Footer>` server components, each making independent DB queries. React's `cache()` only deduplicates within a single render pass — it provides **zero cross-page deduplication**.

**Connection demand per page render:**
- Header: `getProducts(lang)` → 2 SQL (find + count)
- Footer: `getProducts(lang)` + `getContactInfo(lang)` → 3 SQL
- Page body: 2-6 SQL (varies by page)
- **Total: 7-11 SQL queries per page**

With 30+ pages rendering concurrently, peak demand hits **56+ SQL queries in flight**, far exceeding the 15-connection server limit.

The error specifically surfaces at `careers/[id]/apply/page.tsx` because its `generateStaticParams()` calls `getJobs(lang)`, which triggers a Payload connection — but this is just the trigger, not the root cause.

## Fix Plan

### Step 1: Remove `generateStaticParams` from careers pages (eliminates build-time DB queries)

**Files:**
- `app/(frontend)/[lang]/careers/[id]/apply/page.tsx` (lines 13-23)
- `app/(frontend)/[lang]/careers/[id]/page.tsx` (lines 20-32)

**Action:** Replace `generateStaticParams` that calls `getJobs(lang)` with a hardcoded return that only generates the 3 language variants (no DB call). The actual job data will be fetched at runtime via ISR (`revalidate = 60` already set).

For `careers/[id]/page.tsx` and `careers/[id]/apply/page.tsx`:
```ts
// BEFORE (calls getJobs → DB connection)
export async function generateStaticParams() {
  const langs = ["en", "fa", "ar"]
  const allParams = []
  for (const lang of langs) {
    const jobs = await getJobs(lang)
    for (const job of jobs) {
      allParams.push({ lang, id: String(job.id) })
    }
  }
  return allParams
}

// AFTER (no DB call — ISR handles dynamic params)
export const dynamicParams = true
export async function generateStaticParams() {
  return [] // Let ISR generate pages on-demand
}
```

**Note:** With `dynamicParams = true` and `revalidate = 60`, pages are rendered on first request and cached for 60 seconds. No pre-generation needed.

### Step 3: Make Header a client component (eliminates per-page DB queries)

**File:** `components/layout/header/index.tsx`

**Action:** Convert the Header to fetch products client-side or pass data from a layout. The simplest fix is to make it a client component that fetches navigation data from a static JSON file or API endpoint, rather than querying Payload on every server render.

**Alternative (simpler):** Create a shared layout-level data fetch that populates Header/Footer props once, rather than each component independently querying the DB.

### Step 4: Make Footer data static (eliminates per-page DB queries)

**File:** `components/layout/footer.tsx`

**Action:** The footer's product categories and contact info change rarely. Fetch once at layout level and pass as props, or use a static JSON file.

**Action:** Remove `getJobs` from the import since `generateStaticParams` no longer calls it.
